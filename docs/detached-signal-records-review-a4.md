# Adversarial review: detached-signal-records.md, revision 4

Verdict: v4 is REFUTED, two FATAL. The identity-blindness that killed the v3 link gate was not eliminated — it moved into hardening 1's restore-site validation, and hardening 5 hands the attacker the synchronous recycle it needs. Hardening 5 itself, taken at its word ("hardening 5's exit check may then grow the arena"), runs arena migration at frame exits while host-tier closures of the retiring generation are still on the stack — the exact generation split the attach bracket exists to prevent. Two FATAL, five MAJOR, three MINOR.

## Findings

**1. FATAL — Restore-site validation reads the live flag of whatever occupies the saved id: a disposed-then-recycled subscriber is re-installed through the public frame setter, and hardening 5 makes the recycle synchronous.**
The spec claims "a stale id can never be re-installed after its record was freed **or recycled**." The validation it prescribes — read the saved id's live flag, restore 0 if dead — cannot support the "or recycled" half: `activeSub` and every saved `prev` are bare ids with no generation (index.ts:301, 349-353), and a recycled record's occupant is Live. This is byte-for-byte the identity-blindness that killed the v3 gate (a3-2, b3-2), relocated from link time to restore time. Scenario, all public API:
1. `const A = effectId(noop)` — record X.
2. `setActiveSub(A); const saved = setActiveSub(0)` — the documented save/restore pattern; `saved === A`.
3. `dispose(A)` — X queued on `pendingFree` (activeSub is 0, hardening 1's clear correctly does nothing).
4. `trigger(() => {})` — returns to depth zero; **hardening 5's exit boundary work sweeps**, X drops onto `nodeFreeStack` (system.ts:1263-1292).
5. `const B = effectId(fn)` — `allocNode` pops X (system.ts:1224-1241): impostor B lives at A's id.
6. `setActiveSub(saved)` — validation loads `M[X + Flags]`: Live (it is B). Passes. `activeSub = A(=B)`.
7. Any tracked read — including a detachable signal's first read, which attaches — links into B. B re-runs on writes to signals it never read; the detached signal's hook environment is pinned by B's lifecycle.
Under today's code, steps 4-5 require a microtask yield or an 8,192-record backlog plus a creation-path boundary (b3-2 needed a yield). With hardening 5, every frame exit is a sweep site, so the construction is one synchronous straight line — **yes, hardening 5 makes this strictly easier to hit**. The record generation the fix needs already exists (`NodeSlot.Gen`, system.ts:151); validation would have to compare (id, gen) pairs saved at every save site, which the spec nowhere requires. Defeats: hardening 1's central claim, obligation 12, and the a3-2/b3-2 resolution claims in "How v4 answers the v3 reviews."

**2. FATAL — Hardening 5 runs deferred growth at depth-zero frame exits while host-generation closures still hold the retiring arena: exit-time migration reintroduces the generation split the attach bracket prevents.**
The spec is explicit that exits may grow ("hardening 5's exit check may then grow the arena," Mechanics step 1; "Maintenance (the free-record sweep, deferred growth)... Frame-bracket exits check for pending boundary work at depth zero"). But `EnterDepth === 0` means no *user-code* frame is live — not that no *host closure* is live. `grow()` retires the engine and zeroes the old arena (system.ts:835-854, 1080-1092), and the `allocated` callback rebuilds the host from `host.state()` (index.ts:203-222), a snapshot of the old generation's mid-flight tracking scalars. Two callers that hold pre-exit state at exactly the moment the spec fires:
- **`effectId`'s own finally.** Order today: `--runDepth; --M[SysSlot.EnterDepth]; activeSub = prevSub; M[id+Flags] &= ~RecursedCheck` (index.ts:512-519). The exit check at the decrement runs `grow()` *before* the restore: `host.state()` captures `activeSub === id` (the exiting effect) and the new generation boots with it — permanently, because the old closure's `activeSub = prevSub` writes a dead variable. Every subsequent top-level read tracks into that effect. The trailing `M[id+Flags] &= ~RecursedCheck` also lands in the zeroed retired arena, so the real record keeps `RecursedCheck` forever and `propagate` routes its notifications through the recursion arm (system.ts:1461-1465) — the effect stops being notified normally.
- **`drainQueue` between queued effects.** `run(E1)` exits at depth zero mid-flush (index.ts:883-898); growth here leaves the rest of the loop reading `M[id + NodeSlot.Gen]` from the zeroed arena: gen>0 entries mismatch and are silently skipped; gen-0 entries "pass," run against zeroed flags, fall through `run()`'s re-arm branch (index.ts:852-855), and come out permanently disarmed. Same shape for `getSlow` at `updateComputed`'s exit: the follow-on `M[id + NodeSlot.Subs]` load and `shallowPropagate` walk the zeroed arena (index.ts:958-977) and drop the promotion wave.
Sweep-at-exit is survivable (queues are gen-guarded); growth-at-exit is not, at any placement of the check — the only growth sites that are actually safe are ones with an empty host stack (today's microtask). Defeats: hardening 5, the step-1 "maintenance stays reachable" claim, obligations 16/20, and the a3-5/b3-5 resolution mechanism.

**3. MAJOR — Hardening 1's site enumeration is incomplete on both halves: three restore sites are missing, two saved-id channels are not `activeSub`, and free paths that never pass through `dispose()` leave a dead id in `activeSub` with no validation before the next tracked read.**
Restore sites in the code: `setActiveSub` (index.ts:349-353), `run` (848), `updateComputed` (811), `trigger` (666), **`effectId` (517), `effectScopeId` (557), `runCleanup` (909)**. The spec's list — "the public frame setter and the run/update/trigger exits" — omits the last three. An unvalidated `effectId` finally re-installs a parent disposed by its child's body, and the parent's remaining reads then `linkInsert` into a freed record; the sweep's `freeNode` zeroes it without unlinking (system.ts:1243-1253) — the v1-finding-3 ghost edge, reborn through an unlisted site. Beyond `activeSub`:
- **`currentScope`** is the same dead-id class, unaddressed. `effectScope(() => { dispose(getActiveSub()); signalId(0); })` crashes today: `disposeEffect` clears `owned[idx]` (index.ts:597-609), then `signalId`'s region push dereferences it (index.ts:433-435). TypeError at best; with recycling, silent adoption of a live signal into a stranger's region.
- **`triggerScratch`** is a cached id consumed without validation (index.ts:640-643). `trigger(() => { dispose(getActiveSub()); })` frees the persistent scratch; the next `trigger()` absolute-stores `Watching|RecursedCheck` into whatever record recycled it — with hardening 5, recycled at the previous trigger's own exit — stomping a live node's flags word.
- **Clear-side coverage:** `activeSub` is a host closure variable; the kernel's free paths cannot see it. The spec never says where "disposal ... clears activeSub" hooks in, and any host-side placement (dispose/disposeEffect) misses `freePendingRegions` (microtask, index.ts:611-629) and `orphan`/`reclaimOrphan` (registry, system.ts:1777-1802). Manual frame held across a microtask + scope disposal of the frame's subscriber = dead id sits in `activeSub`, the next read links into the freed record, and no restore-site validation ever intervenes — the exact "window between disposal and the next validation" the design claims cannot exist. Defeats: hardening 1's "every site" claim, obligations 12-13.

**4. MAJOR — Hardening 3's exit drop does not re-check subscriber emptiness: a computed unwatched mid-update that gains a new subscriber before exit has its dependencies stripped while watched, and goes permanently stale.**
The pending bit is set by the dispatch; the spec's exit action is unconditional ("the update exit performs the drop if the bit is set"). Scenario:
1. `E1 = effect(() => c())` over `c = computed(getter)`, `c` reads `s`.
2. `s(2)` → `run(E1)` → `c` recomputes. Inside the getter: `stopE1()` — the forward walk (hardening 2) unlinks E1→c, `c`'s subs empty, unwatched dispatch finds `c` mid-update, sets the bit.
3. Still inside the getter: `const saved = setActiveSub(0); e2 = effect(() => c()); setActiveSub(saved)`. E2's run reads `c` mid-update — `getSlow` falls to the stale-read-by-contract branch and **links c→E2** (index.ts:979-985); `hostWatchedNode` re-arms `HostStarted` (system.ts:1418-1432). `c` is watched again.
4. Getter returns; update exit sees the bit and drops `c`'s deps. `c` is now watched by a live E2 with an empty dependency list: `s(3)` never reaches it. E2 renders a stale value forever.
Also unspecified: whether the bit is cleared when the update exits by throw — if not, the *next* update re-tracks and then exit-drops its fresh deps, same staleness one write later. The exit drop must be conditional on the sub list still being empty and must clear the bit on all exits; the spec says neither. Defeats: hardening 3, obligation 19.

**5. MAJOR — Hardening 2 flips the teardown cascade from newest-first to oldest-first (observable), and its idempotence claim holds only if the walk normatively re-reads the list head.**
Today `freeNodeId`'s reverse dep walk disposes child effects newest-first — standard destructor order, and the order `reset()` separately promises ("newest records first," system.ts:930-935). A head-forward walk runs child cleanups in creation order: a child created after (and depending on resources of) an earlier sibling now has its cleanup run *after* the sibling's resources are torn down. The spec neither acknowledges nor pins this semantic change, and leaves the library internally inconsistent with its own reset ordering. Separately: "idempotent (the head empties as it goes)" is only true for a loop that re-reads `M[sub + Deps]` each iteration. A cached-next loop (`l = unlink(l, sub)`, the purgeDeps shape, index.ts:936-942) is not idempotent under re-entrancy: unlinking child A cascades into A's user cleanup (`disposeEffect` → `runCleanup` runs inside the walk, index.ts:587-596), which may dispose sibling B — freeing the very link the walk cached as next, and `freeLink`/`allocLink` recycle links immediately (system.ts:1300-1326). The spec must make re-read-the-head normative or the "fix" reintroduces the double-unlink corruption it claims to close. Defeats: hardening 2, obligation 14's completeness claim.

**6. MAJOR — The reset()-in-open-batch state that obligation 21 blesses corrupts the batch counter: the survivor `endBatch()` drives `batchDepth` to −1 and flushing dies system-wide.**
`resetGuard` checks only `EnterDepth` (system.ts:1152-1156); `startBatch` never touches it (index.ts:375-377) — so reset inside an open batch already passes the guard today, contradicting `reset()`'s own doc ("Throws if called during ... batch," system.ts:390). v4 makes this state *normative* ("including values staged inside an open batch at reset time," obligation 21). The staged value itself survives (the hook copies `pendingVals` — correct). But `host.resetState()` zeroes `batchDepth` (index.ts:320-333), and the caller's still-open `endBatch()` then decrements 0 → −1: `!--batchDepth` is false, so no flush; thereafter `setHot`'s `!batchDepth` is false for every write (index.ts:1032), effects queue forever, and `flushEffects()` throws its in-a-batch error (index.ts:386-388). The contract section calls this "strictly better" without defining the survivor bracket's behavior; the claimed state is reachable and leaves the flush machinery dead. Defeats: §`reset()` contract, obligation 21.

**7. MAJOR (pre-existing, inherited and amplified) — Entry-point boundary growth already splits generations under mid-flight host closures: a first `trigger()` after an in-frame 3/4 crossing is a silent no-op and loses the EnterDepth bracket.**
`trigger` allocates its scratch *before* bumping `EnterDepth` (index.ts:645 vs 662); `facade.allocNode` runs `maybeBoundary` first (system.ts:966-969, 1140-1150). If a prior effect body pushed the bump pointer past `growAt` (setting `growPending` where `maybeBoundary` is skipped), the next top-level `trigger()` grows mid-setup: the running `trigger` closure belongs to the retired generation — its `activeSub = id` writes the dead host's variable, so the fn's reads (dispatched through the re-pointed module lets into the *new* host) track nothing; its finally walks deps in the zeroed arena and propagates nothing; and its `++/--M[SysSlot.EnterDepth]` brackets the *retired* record 0, so the new arena runs the fn unbracketed (growth and even `reset()` are reachable mid-trigger). The user's in-place mutations are silently un-notified. `signalId` has a sibling defect: after a mid-call growth, `M[id + NodeSlot.Gen]` reads the zeroed retired arena, so a scope-owned recycled record is registered with gen 0 and the region free later no-ops — a leak. This undermines the v3 reviews' "migration-mid-attach prevention: not refuted" certification — the attach bracket is sound, but the boundary machinery around it is not — and hardening 5 multiplies exactly this growth-under-live-host-frames pattern (finding 2). Relevant to §7 of the brief: not churn damage, but a core defect all four rounds certified around.

**8. MINOR — Hardening 4 is a semantic change presented as a pure leak fix.**
Today an `effect(fn)` whose first run throws keeps its pre-throw links, stays Watching, and re-runs when those dependencies change (index.ts:512-519 restores and returns nothing; the record, fns entry, and links stay live) — matching the flush machinery's own philosophy of re-arming survivors after a throw (index.ts:868-880). Hardening 4 kills it. Defensible, but it changes observable behavior for retry-shaped code, diverges from upstream parity, and the spec sells it as fixing only a leak. Defeats: hardening 4's framing; obligation 18 should pin the semantic change explicitly.

**9. MINOR — Stale renumbering: the limitation section credits "hardening 2" with disposing a first-run effect that dies to arena exhaustion; that is hardening 4 after the v4 renumbering** ("hardening 2 disposes a first-run effect that dies to it," §Documented limitation). Same slip risks tests being written against the wrong prerequisite. Defeats: §Documented limitation's internal consistency.

**10. MINOR — Gate residue.** (a) Hardening 5's steady-state gate says "a bounded arena over one million synchronous trigger iterations" — "bounded" has no number; an arena that doubles to `maxCapacity` and stops is bounded. State it as no-growth / ≤ initial capacity + a constant. (b) The oscillation micro's `K` is unspecified; the flush amortizes ∝ K so any K is arguably fair, but the spec should fix it. (c) The noise floor `1 + 2×RMAD` is computed from the baseline's own runs: a deliberately noisy baseline environment loosens every gate simultaneously; the protocol needs a max-noise rejection rule. Defeats: §Costs and gates (residually — this is far better than v1-v3's gates).

## Not refuted (genuine effort)

- **The detach mechanics proper**: hook-presence dispatch gate, `pendingVals` copy-out (setHot stores pending first, index.ts:1025; commit copies pending→current, index.ts:778), cleared-hook double-dispatch no-op, re-read-before-sweep attaching a fresh record — not refuted.
- **Attach's try/finally bracket including the step-1 throw** (a3-6/b3-6): not refuted — with the bracket normative, the wedge is closed; maintenance and reset stay reachable.
- **Region exclusion via the dedicated attach path**: not refuted.
- **The taxonomy table**: verified against code — default callables are owner-registered, never region-owned (index.ts:1323-1333, 424-435); computeds register at creation (index.ts:466-482); accurate.
- **Reset-sweep masquerade immunity via the hook gate**: not refuted — link records never receive hook entries; the misdispatch parenthetical (link `Version` bits read as flags past cycle 8192, system.ts:935-944 + LinkSlot.Version at offset 0) is a real, correctly-characterized kernel bug.
- **Hardening 3's never-watched exemption** (b3-4): not refuted — the dispatch only fires on a real last-unlink, and never-watched computeds carry no `HostStarted`.
- **Replacement-child-survives-as-root semantics**: not refuted — matches gate-free mechanics; today's variant additionally leaves a ghost parent edge, so v4's behavior is the cleaner of the two.
- **Mass-first-read limitation**: honestly stated; not refuted (modulo finding 9's renumbering).
