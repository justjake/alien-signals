dalien-signals

A signal is a value that remembers who read it. When it changes, everything computed from it — and nothing else — updates. There is no explicit subscription step and no re-rendering pass: the dependency graph assembles itself while code runs, and a write touches exactly the part of it that could have changed. This page explains how dalien-signals does that, with the real engine running in every demo.

Two of the controls illustrate specific mechanisms. Equality cutoff: each cell rounds its output to a coarse step, so as a ripple fades, cells begin producing the same value they held before, and the cascade stops at that point. Disabling it makes the recompute cones visibly taller. Invalidate everything writes one signal that every cell reads, forcing all twenty thousand nodes to recompute in a single frame; the timer reports the cost of a full-graph pass, a cost the design avoids in normal operation.

The three primitives

Everything above is built from three functions. A signal stores a value: call it with no argument to read, with an argument to write. A computed derives a cached value from whatever signals and computeds its function reads. An effect runs a function now, and again whenever a value it read changes; rendering, logging, and other side effects belong there. 

import { signal, computed, effect } from "dalien-signals";

const count   = signal(1);
const doubled = computed(() => count() * 2);
const isEven  = computed(() => count() % 2 === 0);

effect(() => console.log(doubled(), isEven()));
count(2); // logs: 4 true

Stepping from 1 to 3 shows the update rule precisely: the run counter's effect reads both computeds, but it re-runs only when one of them produces a new value. doubled changed; even? evaluated to no again, the same answer as before, so nothing that depends only on even? was disturbed. This is equality cutoff — the same rule that stops the ripples in the field above. Note that no relationship was declared anywhere: reading inside a computed or effect is the subscription.

How a write becomes an update

dalien-signals is a push-pull engine. A write does not recompute anything by itself; it records what may have changed, cheaply, and the work happens later, on demand:

  1. Push staleness. Writing a signal marks it Dirty and walks its subscriber lists, marking each downstream node Pending — "something under you may have changed." No user code runs during this walk; it's a few integer writes per node.
  2. Queue effects. Any effect the walk reaches goes into a queue, once, no matter how many paths led to it.
  3. Pull and verify. When an effect runs — or when you read a computed — the node checks its dependencies: did anything I read actually produce a new value? A Pending chain resolves top-down; a node whose inputs all came out equal clears its flag and reports "nothing changed," cutting the cascade.
  4. Stamp the verdict. Every committed write increments one global version counter. When a computed finishes verifying, it stores that version; a later read compares the two numbers, and if they match, the value is provably current — the read returns in a couple of loads without walking anything.

The model below — two signals feeding a subtotal, a total, and one effect — narrates each operation and draws its graph live. The batch button issues two writes that produce a single effect run; writing an unchanged value produces no work at all. Disposing the effect removes the computeds' last subscribers, and they drop their own dependency edges in turn: an unwatched computed keeps no bookkeeping that nothing will ask about.

Memory layout: eight integers per node

This is where dalien-signals departs from most implementations. Signal libraries typically allocate an object per node, wired with object references; the garbage collector then traces that web on every collection. dalien-signals stores the whole graph in one Int32Array — an arena — carved into 32-byte records of eight int32 slots. A "node" is just the index where its record starts:

0 · Flags
kind tag + state bits: Mutable, Watching, Dirty, Pending, …
1 · Deps
head of the dependency list — points at a link record
2 · DepsTail
the re-track cursor into that list
3 · Subs
head of the subscriber list — also a link record
4 · SubsTail
tail of the subscriber list
5 · Gen
generation counter, so stale ids of freed records miss
6+7 · Version
one float64 (via a shared-buffer view): "verified as of global version N"

Edges are records in the same array: a link record names a dependency, a subscriber, and the four neighbors that thread it into both of their lists. "Walking the subscriber list" means following integers from slot to slot — no pointer chasing across the heap, no objects for the collector to trace, and neighboring records share cache lines. Example: Spreadsheet

The spreadsheet below is built on the same engine. Each cell is a signal (the typed text) plus a computed (what it evaluates to). Formulas start with = and are plain JavaScript with one extra function: GET('A:1') reads another cell. Because the formula runs inside the cell's computed, every GET records a real dependency edge in the arena. Editing a formula rewires those edges; the memory view below shows link records appearing and aging out as it happens.
