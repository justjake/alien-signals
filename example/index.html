dalien-signals

A signal is a value that remembers who read it. When it changes, everything computed from it — and nothing else — updates. You never subscribe, never diff, never re-render the world: the dependency graph assembles itself while your code runs, and a write touches exactly the part of it that could have changed. This page explains how dalien-signals does that, with the real engine running in every demo.

Two things worth trying. Equality cutoff: each cell rounds its output to a coarse step, so as a ripple fades, cells start producing the same value they had before — and the cascade stops right there. Toggle it off and watch the shimmer cones grow taller. Invalidate everything writes one signal that every cell reads, forcing all twenty thousand nodes to recompute in a single frame — the timer shows what a full-graph pass costs, which is the price this library is designed to almost never pay.

The three primitives

Everything above is built from three functions. A signal stores a value: call it with no argument to read, with an argument to write. A computed derives a cached value from whatever signals and computeds its function reads. An effect runs a function now, and again whenever a value it read changes — that's where rendering, logging, and other side effects live. 

import { signal, computed, effect } from "dalien-signals";

const count   = signal(1);
const doubled = computed(() => count() * 2);
const isEven  = computed(() => count() % 2 === 0);

effect(() => console.log(doubled(), isEven()));
count(2); // logs: 4 true

Notice what the run counter does when you step from 1 to 3: the bottom effect reads both computeds, but it re-runs only when one of them produces a new value. doubled changed, even? came out no again — the same answer as before — so nothing that depends only on even? was disturbed. That's equality cutoff, the same rule that stops the ripples in the field above. And nobody declared any of these relationships: reading inside a computed or effect is the subscription.

How a write becomes an update

dalien-signals is a push-pull engine. A write doesn't recompute anything by itself — it publishes doubt, cheaply, and the real work happens later, on demand:

  1. Push staleness. Writing a signal marks it Dirty and walks its subscriber lists, marking each downstream node Pending — "something under you may have changed." No user code runs during this walk; it's a few integer writes per node.
  2. Queue effects. Any effect the walk reaches goes into a queue, once, no matter how many paths led to it.
  3. Pull and verify. When an effect runs — or when you read a computed — the node checks its dependencies: did anything I read actually produce a new value? A Pending chain resolves top-down; a node whose inputs all came out equal clears its flag and reports "nothing changed," cutting the cascade.
  4. Stamp the verdict. Every committed write increments one global version counter. When a computed finishes verifying, it stores that version; a later read compares the two numbers, and if they match, the value is provably current — the read returns in a couple of loads without walking anything.

Step through it yourself. This little shop — two signals feeding a subtotal, a total, and one effect — narrates each operation and draws its graph live. Try the batch: two writes, one effect run. Try writing the same value: nothing happens at all. Dispose the effect, and watch the computeds lose their subscribers and drop their own dependency edges — an unwatched computed doesn't spend memory on bookkeeping nobody will ever ask about.

A node is eight integers

Here's the part that makes dalien-signals unusual. Most signal libraries allocate an object per node and wire them together with object references; the garbage collector then traces that web on every collection. dalien-signals stores the whole graph in one Int32Array — an arena — carved into 32-byte records of eight int32 slots. A "node" is just the index where its record starts:

0 · Flags
kind tag + state bits: Mutable, Watching, Dirty, Pending, …
1 · Deps
head of the dependency list — points at a link record
2 · DepsTail
the re-track cursor into that list
3 · Subs
head of the subscriber list — also a link record
4 · SubsTail
tail of the subscriber list
5 · Gen
generation counter, so stale ids of freed records miss
6+7 · Version
one float64 (via a shared-buffer view): "verified as of global version N"

Edges are records in the same array: a link record names a dependency, a subscriber, and the four neighbors that thread it into both of their lists. "Walking the subscriber list" means following integers from slot to slot — no pointer chasing across the heap, no objects for the collector to trace, and neighboring records share cache lines. Finale: a spreadsheet is a dependency graph

A spreadsheet is the oldest reactive system in computing, so let's end with one. Each cell is a signal (what you typed) plus a computed (what it evaluates to). Formulas start with = and are plain JavaScript with one extra function: GET('A:1') reads another cell. Because the formula runs inside the cell's computed, every GET records a real dependency edge in the arena — edit a formula and watch link records appear and age out in the memory view on the right.
